# watch-list-desktop (Electron, Windows, single-user mode)

A wrapper around [`../src`](../src) that turns the single-user watch-list
into a regular Windows application — no Docker, no browser tab, no
installer, no editing `docker-compose` by hand. Two build outputs to choose
from: a `.zip` (unzip once, then run the `.exe` directly — fast startup) or
a single portable `.exe` (nothing to unzip up front, but it self-extracts on
every launch — slower startup). See "Building the Windows distributables"
below for the trade-off.

**Guiding rule for this wrapper: the repo root stays untouched unless
necessary.** Almost everything needed for the desktop build lives inside
`electron/` — its own `package.json`, its own `node_modules`, its own copy of
the server code. The one exception is that `../src/server.js` can listen on
a specific `HOST` in addition to all interfaces (see the firewall note
below): a backwards-compatible addition (default behavior is unchanged) that
the Docker build doesn't need but isn't hurt by either, so it wasn't
duplicated into a fork-only file. The regular `npm start` / Docker image
from the repo root keep working exactly as before.

## Architecture

```
┌─────────────────────────────────────────────────────────────┐
│ Electron main process (electron/main.js)                     │
│                                                                │
│  1. Tries a fixed port, 47823 (falls back to a random one)    │
│  2. Prepares SESSION_SECRET (generated once, stored in        │
│     data/session-secret.txt next to the .exe)                 │
│  3. Sets DB_PATH → data/watchlist.db next to the .exe          │
│  4. Sets HOST=127.0.0.1 (loopback only)                        │
│  5. require('./app/server.js')  ──────────────┐                │
│                                                 │                │
│                                                 ▼                │
│                              ┌───────────────────────────────┐  │
│                              │ Express server (a copy of src/)│  │
│                              │ listens on http://127.0.0.1:PORT│ │
│                              │ ALLOW_REGISTRATIONS unset →     │  │
│                              │ single-user mode                │  │
│                              └───────────────────────────────┘  │
│                                                 ▲                │
│  6. BrowserWindow.loadURL(...)  ───────────────┘                │
└─────────────────────────────────────────────────────────────┘
```

No IPC, no renderer code that talks to Node — the Electron window simply
opens the local web server, the same way a regular browser would. The
server and UI are literally the same code as the Docker image.

## Folder layout

```
electron/
  main.js               Electron main process — startup/port/path logic
  package.json           Own dependencies (electron, electron-builder, plus
                         the server's runtime deps: express, ejs,
                         better-sqlite3, ...)
  scripts/
    sync-src.js            Copies ../src → ./app (generated folder)
    fetch-win-natives.js   Downloads a prebuilt Windows binary for
                           better-sqlite3 (needed for cross-building off
                           Windows, see below)
  app/                    GENERATED by sync-src.js, not committed, not edited
  build/
    icon.ico              App icon (optional, drop it in before building —
                           without it, the default Electron icon is used)
  dist/                   GENERATED by electron-builder: dist/Watch List-<version>-win.zip
  .gitignore              node_modules/, app/, dist/, data/
```

`app/` and `dist/` are build artifacts, not source, hence `.gitignore`. Only
`main.js`, `package.json`, `scripts/`, `build/icon.ico` (if you add one), and
this README belong in version control.

## How this relates to the original server

`../src/server.js` already supports everything needed through environment
variables — this wrapper just sets them in `main.js` before `require`,
without touching a single line of the original source:

| Variable              | What the original does                       | What the Electron wrapper sets              |
|------------------------|-----------------------------------------------|--------------------------------------------|
| `ALLOW_REGISTRATIONS` | `false` by default = single-user mode          | not set at all (stays `false`)             |
| `DB_PATH`             | defaults to `./data/watchlist.db`              | `data\watchlist.db` next to the .exe       |
| `SESSION_SECRET`      | has to be entered by hand in compose           | generated once, stored next to the .exe    |
| `PORT`                | defaults to `3000`                             | fixed `47823`, falls back to a random free port if taken (see below) |
| `HOST`                | unset = listens on all interfaces (needed by Docker) | `127.0.0.1` — loopback only (see below) |
| `HTTPS`               | optional, needs a certificate                  | not set — the server is loopback-only anyway |

Since `ALLOW_REGISTRATIONS` is never enabled, the login/registration routes
from `../src/routes/auth.js` are never even mounted (`server.js` handles
that itself via `if (ALLOW_REGISTRATIONS) { ... }`) — nothing had to be cut
out separately.

## Getting it running for development

```powershell
cd electron
npm install       # pulls in electron, electron-builder, and the server's runtime deps
npm start          # runs sync first (copies ../src → ./app), then launches electron .
```

`npm start` runs `sync` every time, so changes in `../src` are picked up
automatically on the next `npm start` — no manual sync step needed (it only
matters for building the `.exe`, see below — `dist:win` also calls `sync` on its own).

## Building the Windows distributables (.zip and portable .exe)

```powershell
cd electron
npm install
npm run dist:win
```

`win.target` in the config is `["zip", "portable"]`, so one command builds both:

- **`electron/dist/Watch List-<version>-win.zip`** — the unpacked
  application (`Watch List.exe` + DLLs/resources). Unzip it once anywhere
  (even a USB stick) and run `Watch List.exe` directly from then on —
  startup is fast (typically 1–3 seconds) since extraction only happens once,
  not on every launch.
- **`electron/dist/Watch List <version>.exe`** — a single self-extracting
  file (NSIS `portable`). Nothing to unzip ahead of time — but that's
  exactly why every launch self-extracts again into a temp folder
  (100+ MB), which antivirus software periodically rescans — startup is
  noticeably slower (7–9 seconds). This target was dropped in favor of just
  `zip` early on for that reason, then brought back as a second option once
  the other Windows quirks (firewall prompt, focus loss after an external
  link) were fixed and stopped compounding with "and it's also slow to start."

Both targets share the same `main.js` — `getBaseDir()` already handles both
cases (`PORTABLE_EXECUTABLE_DIR` for the portable build, `app.getPath('exe')`
for the zip), so `data\` ends up next to the real `.exe` either way.

Built and verified from WSL2 (cross-building the Windows target from Linux)
— details and gotchas below, in the better-sqlite3 section. Building
directly on Windows uses the same commands; the cross-build wrinkles (wine)
simply won't apply there.

## Distributing builds

The zip build is well over 100 MB, which is GitHub's hard per-file limit for
a normal `git push` — pushing it as a regular tracked file will be rejected.
Because of that, `dist/` is listed in `.gitignore` here and the build
artifacts are **not** meant to be committed to the repository. The
recommended way to distribute them is to attach `dist/Watch List-<version>-win.zip`
and `dist/Watch List <version>.exe` as assets on a
[GitHub Release](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)
for the corresponding tag — Releases support files up to 2 GB each with no
extra setup (Git LFS is the alternative if you'd rather keep them versioned
directly in git).

## Native module: better-sqlite3

`better-sqlite3` is compiled against a specific runtime ABI (Node vs.
Electron use different ABIs even on the same V8 version, and Windows vs.
Linux are different binaries entirely). Because of that:

- In `electron/package.json` it's declared as a **separate dependency**,
  installed into `electron/node_modules` — a physically separate copy from
  the root `node_modules` (which is used by Docker/`npm start` from the
  repo root and isn't touched here).
- `asarUnpack: ["**/*.node"]` in the config is required — Electron can't
  load native `.node` bindings straight out of an `.asar` archive.

### Running locally (`npm start`) on the same OS you're building on

`npm run rebuild` (`electron-builder install-app-deps`) compiles the module
from source against the Electron ABI for the **current OS**. This works
fine if you're developing/testing on Windows and building for Windows (or on
Linux, for Linux). It needs build tools (Visual Studio Build Tools with the
C++ workload on Windows; usually already available `gcc`/`make`/`python3` on Linux).

### Cross-building the Windows target from a non-Windows machine (e.g. WSL)

There's a gotcha here: `electron-builder install-app-deps` / `@electron/rebuild`
**cannot cross-compile** — it always builds for the current OS the process
runs on. If you build `dist:win` from Linux/WSL with a plain
`electron-builder install-app-deps`, the build completes with no errors, but
the resulting `.exe` ends up with a **Linux** build of `better_sqlite3.node`
(an ELF file) inside it — that would crash on startup on real Windows.
Easy to check: `file build/Release/better_sqlite3.node` should report
`PE32+ executable ... for MS Windows`, not `ELF ... GNU/Linux`.

The fix is to not compile the module for Windows on Linux at all (there's no
compiler for that target anyway) and instead grab an already-built Windows
binary. `scripts/fetch-win-natives.js` does exactly that: it downloads the
official prebuilt better-sqlite3 binary for `win32-x64` matching the current
Electron version via `prebuild-install --platform=win32 --arch=x64
--runtime=electron`, with no compilation involved. `build.npmRebuild: false`
in the config keeps `electron-builder` from overwriting that file with its
own (Linux) rebuild. The script is already wired into `npm run dist:win`, no
need to run it separately; building directly on Windows, it still runs and
just downloads the same binary instead of compiling — safe there too.

Cross-building the Windows target on Linux/WSL also needs `wine`
(`electron-builder` uses `rcedit.exe` to patch the `.exe`'s metadata — name,
version — and runs it through wine): `sudo apt install wine64` and,
additionally, `sudo dpkg --add-architecture i386 && sudo apt install
wine32:i386` (otherwise the 32-bit `rcedit-ia32.exe` won't run). None of
this is needed when building directly on Windows — it's all native there.

## Where user data lives

Data lives next to the `.exe` itself, in a `data\` subfolder — not in
`%APPDATA%`. Under the hood: `main.js` uses
`path.dirname(app.getPath('exe'))` — the folder where the running
`Watch List.exe` actually lives (for the `.zip` build, with no
self-extraction, that's exactly the folder the user unzipped the archive
into — no temp copy involved). In dev mode (`npm start`, unpackaged),
`app.isPackaged === false`, and `data\` is created directly inside `electron\`.

Inside `data\`:

- `watchlist.db` (+ `watchlist.db-wal` / `watchlist.db-shm` while the server
  is running) — the database: titles, covers
- `session-secret.txt` — the express-session secret (`0600` permissions)

So moving the app to a USB stick or another machine means taking the **whole
unzipped folder** (not just `Watch List.exe` — the DLLs and Electron
resources next to it are required for it to run) along with the `data\`
folder that appears inside it after the first launch. To reset the app,
delete `data\` next to the `.exe`.

## Notable implementation details

A few things in `main.js` exist specifically to fix real issues found while
testing on actual Windows machines:

- **Fixed port (47823).** Theme, grid/table view, and other client-side
  preferences are stored via `localStorage`, which in Chromium is scoped to
  the origin — port included. A random port on every launch meant a new
  origin every time, so `localStorage` from the previous run became
  unreachable — settings appeared to "reset" on every start. Trying one
  fixed port first (falling back to a random one only if it's taken by
  something else) keeps the origin stable across launches.
- **`HOST=127.0.0.1`.** Listening with no host binds to all interfaces
  (`0.0.0.0`), which is what Docker needs, but on Windows it made the
  firewall prompt for network permission on every first launch. Since the
  desktop app never needs to be reached from outside the machine, binding
  to loopback only removes the prompt entirely.
- **Focus fix after `window.confirm()` + navigation.** External links (see
  `setWindowOpenHandler`) hand OS focus to the system browser, which is
  expected. Separately, after a native `confirm()` dialog (e.g. deleting a
  title) followed by a page navigation, Chromium's `webContents` could drift
  into `blur` on its own while Electron still reported the window as
  focused — the visible symptom was "the input field ignores the keyboard,
  only clipboard paste works." `setupFocusFix` in `main.js` re-syncs focus
  on the relevant events and, for the stuck case, forces Windows to
  recompute focus via `minimize()+restore()+focus()`.
- **`.badge-planned` contrast fix** (in `../src/public/style.css`) — the
  "planned" status badge had a hardcoded dark background with a
  theme-dependent text color, which also went dark in light mode, making it
  unreadable. This was a bug in the shared UI code, not the Electron
  wrapper, so it applies to the Docker build too.
- **Cover not wiped out by a failed refetch** (in
  `../src/routes/entries.js`) — `POST /:id/refetch` used to overwrite the
  cover with whatever `resolveCoverFields()` returned even when that came
  back empty (source has no image, or download failed). Fixed to only
  overwrite the cover when a new one was actually fetched. Also not
  Electron-specific — applies to the Docker build as well.

## Deliberately left out (not needed for a single-user .exe)

- Login/registration routes — never mounted (see the table above), nothing
  had to be stripped from the copy.
- HTTPS/certificates — the server only listens on `127.0.0.1`, never exposed
  externally, so TLS would be redundant.
- Docker/compose-specific things (external `PORT`, the `/data` volume) —
  replaced by `data\` next to the `.exe` (see above).

## Updating from upstream

If something changes in `../src` (a new feature, a fix), sync it with
`npm run sync` (or just the next `npm start` / `npm run dist:win`, which do
this on their own). `scripts/sync-src.js` doesn't merge — it fully
overwrites `electron/app/` with the contents of `../src`. If `app/` ever
needs desktop-only manual changes, make them in `../src` instead (if the fix
also applies to the original) or add a small patch step after sync (there
isn't one today — the server runs as-is, unpatched).
